## Purpose

Every documentation artifact in this repo gets exactly one row here, and every
row ends the loop with exactly one verdict. This file is the single place where
"is this document true?" is answered — no verdict lives anywhere else.

## Verdict vocabulary

| Verdict | Meaning |
| --- | --- |
| `pending` | not audited yet (T01 leaves every row here) |
| `TRUE` | verified against the code, kept where it is, unchanged |
| `FIXED` | drift corrected in place — the code won |
| `RECLASSIFIED` | class changed and/or moved/merged into the approved structure |
| `DELETED` | adds nothing; removed (T10 only, after the T09 human round) |

## Rules that bind this ledger

1. **The code is the source of truth.** A doc-vs-code difference is a DOC bug by
   default. If a difference reveals a genuine CODE bug, STOP and escalate as a
   decision — this loop never changes runtime code silently.
2. **No citation, no verdict.** Every `FIXED` row cites the code that
   contradicted the doc (name-based: constant/function/file names, never `:NNN`
   line cites — they rot within days). Every DELETE proposal states what, if
   anything, replaces it. A row with a verdict and an empty Evidence cell is
   invalid and must be sent back.
3. **RECORDS are not audited for present-truth.** `manual-loops/*`, `golden/*`,
   `DRIFT.md`, `cowork/INDEX.md` and friends describe their date. They get
   CLASSIFIED (and dead working notes proposed for deletion in T09), but their
   historical claims are never rewritten.
4. **Prescriptive docs keep their class.** Any clause the code has never honored
   is flagged in the Evidence cell for the T09 round instead of being silently
   "fixed" in either direction.
5. **TAXONOMY.md / SCHEMAS.md / AGENTS.md are read-only** except through an
   escalated decision.

## Class vocabulary

`descriptive` (as-built) · `prescriptive` (contract/how-to the code must obey)
· `future` (design not yet built) · `RECORD` (dated, historical) · `skill`
(agent-facing SKILL.md and its assets) · `script-header` (a shell script's
header comment block, which is that script's document of record) · `fixture`
(sample content shipped as data, not a description of code).

switch, which reads `payload.action_type`, so a job created from this payload
falls to the `default` branch and publishes `execution_failed`. `jobs.md` now

**E8 — two SKB safety helpers are dead code with passing tests.**
`skb-sql-safety.ts` exports `validateSelectOnly()` and `enforceLimit()`.
Neither has a production call site: `rg 'validateSelectOnly|enforceLimit' services`

**E9 (genuine CODE bug — security; escalated, NOT fixed) — the SKB query
builder interpolates unvalidated request input into `sql.unsafe()`.**
`SKBRowsRepository.executeQuery` assembles the executed statement by string
concatenation:

```ts
const whereParts: string[] = [
  `container_id = '${containerId}'`,
  `tenant_id = '${tenantId}'`,
];
…
whereParts.push(`categories @> '${JSON.stringify(options.categories)}'::jsonb`);
…
await sql.unsafe(dataQuery);
```

`containerId` arrives as a bare `@Param("id")` on
`StructuredKBController.query` with **no `ParseUUIDPipe` and no format check**
anywhere on the path, and `categories` is typed only `@IsArray()` on
`QuerySKBDto` (no `@IsString({ each: true })`, no character restriction). The
SKB safety helpers do not cover either value — `isSafe()` and
`validateWhereClause()` are applied to the LLM-produced `whereClause` and
`orderBy` only, which is precisely what `security.md` §"Layer 4" describes as
the part the user "can never control".

A single quote in the path segment therefore breaks out of the literal. The
cheapest demonstration keeps the tenant filter intact and still defeats the
container filter, because `AND` binds tighter than `OR`:

```
POST /api/admin/structured-kb/containers/x' OR '1'='1/query
→ WHERE container_id = 'x' OR '1'='1' AND tenant_id = '<tenant>' …
→ every row of every container in the tenant
```

and the same hole accepts arbitrary trailing SQL. Note the ONE mitigating
fact: `getSql(tenantId)` returns the per-tenant connection, so the blast radius
observed here is cross-container within one tenant rather than cross-tenant —
but the injection point itself is unbounded, and `sql.unsafe` runs whatever it
is handed.

This is behaviour nobody could want, so per ground rule 1 this loop stops at
reporting it. The fix is a code loop, not a doc edit: parameterise the two
literals (postgres.js `sql.unsafe(text, params)` is already used elsewhere in
the same file), or validate `containerId` as a UUID at the controller and
constrain `categories` element-wise — ideally both. `security.md`'s Layer 4
section was left describing the template honestly and now carries a pointer to
this escalation.

**E10 (genuine BUILD-CONFIG bug — escalated, NOT fixed) — two services'
`test` scripts recurse forever and can never run a test.**
`services/proxy-service/package.json` and `services/tenant-service/package.json`
both define their `test` script in terms of `pnpm test`, i.e. themselves:

```jsonc
// services/proxy-service/package.json
"test":             "bun run build && pnpm test",
"test:unit":        "bun run build && pnpm test test/unit",

// services/tenant-service/package.json
"test":             "MONGO_PASSWORD=${MONGO_PASSWORD:-test} pnpm test",
"test:unit":        "MONGO_PASSWORD=${MONGO_PASSWORD:-test} pnpm test test/unit",
"test:integration": "MONGO_PASSWORD=${MONGO_PASSWORD:-test} pnpm test test/integration",
```

`pnpm test` runs the `test` script, which runs `pnpm test`, which runs the
`test` script. `pnpm test:unit` is the same loop one hop later. Neither ever
reaches `bun test`, so **neither service's unit suite is runnable through its
documented entry point**, and proxy-service additionally rebuilds on every
iteration of the loop. A census of the other 18 services
(`rg '"test(:unit)?":' services/*/package.json`) shows every one of them
invokes a real runner directly (`bun test …`, `node --import tsx …`,
`ng test`), so this is an isolated two-file defect, not a house style.

The fix is one word per line — `pnpm test` → `bun test` — but it is a code
change, so this loop stops at reporting. Both READMEs now tell the reader to
call `bun test test/unit` directly and say why. **T09 should also ask whether
these two suites have been executed at all since the scripts were written**,
since nobody running the documented command could have seen a result.

**E11 (genuine CODE bug — escalated, NOT fixed) — a connector registered with
`authType: "oauth2-client"` silently gets NO `Authorization` header.**
connector-admin's DTO accepts five auth types (`adapters.dto.ts`):

```ts
const ADAPTER_AUTH_TYPES = ["none", "api-key", "bearer", "basic", "oauth2-client"] as const;
```

enforced by `@IsIn([...ADAPTER_AUTH_TYPES])` on both the Create and the Update
DTO. Both consumer-side switches test for a DIFFERENT string:

```ts
// packages/shared/src/adapter-auth-headers.ts — applyAdapterAuthHeadersSync
case "oauth2":
  return;
default:
  return;

// packages/shared/src/adapter-client.ts — AdapterClient.injectAuthHeaders
if (adapter.authType === "oauth2") {
  const token = await this.getOAuthToken(adapter);
  headers["Authorization"] = `Bearer ${token}`;
}
```

So a stored `oauth2-client` connector falls through `applyAdapterAuthHeadersSync`'s
no-op `default` branch AND fails `injectAuthHeaders`' equality check: the OAuth2
token is never fetched and no `Authorization` header is ever set. The outbound
call goes out unauthenticated and fails at the target with a 401 that points at
the target, not at us. Note the value is the ONLY one of the five that no
consumer handles — `none`/`api-key`/`bearer`/`basic` all match.
`services/connector-admin/README.md` has carried a "Known mismatch" note about
this since before this audit; T04 verified it against the code and promotes it
to a numbered escalation so it stops being a footnote. T09 must rule which side
moves (rename the DTO value to `oauth2`, or widen both switches) — either is a
one-line change with a data-migration question attached, which is exactly why a
doc loop must not make it.

**E12 — the agent-ai-service skill loader parses YAML with `indexOf(":")`.**
`SkillFileService.parseFrontmatter`
(`services/agent-ai-service/src/modules/skills/skill-file.service.ts`) splits
frontmatter line by line and takes everything after the first colon, skipping
lines without one. It therefore mis-parses every YAML feature beyond flat
`key: value` — a block scalar (`description: >` + indented body) becomes the
literal string `">"`, which is then served to the model as the skill's
description via `loadSkill()`. T04 fixed the one shipped fixture
(`skills/code-review/SKILL.md`, now flat, with a maintainer note) because the
code is the source of truth, but the trap is still armed: the seven
repo-root `skills/*/SKILL.md` files all use `description: >` (that directory is
read by Claude Code's real YAML parser, which handles it), so anyone copying
the house style into `services/agent-ai-service/skills/` reintroduces the bug
silently — `discoverSkills()` only rejects a skill when `name` is missing, never
when a value is nonsense. T09 rules: parse real YAML, or add a guard/lint that
rejects a non-flat frontmatter value in this directory.

**E13 (as-built reachability, escalated NOT fixed) — agent-scheduler-service
cannot schedule anything in the shipped configuration.**
Four independent blockers, each verified in code and now documented in that
service's README under "Known gaps (as-built)":

1. **No tenant discovery.** `JobReaderService.readAllTenantJobs` iterates
   `tenantManager.getKnownTenantIds()`. That set is written only by
   `TenantConnectionManager.getOrCreatePool`, which this service reaches only
   from the private `readTenantJobs(tenantId)` — i.e. only for tenants already
   in the set. Nothing seeds it: no tenant-catalog query, no
   `platform.tenant.ready` subscription, no `ensureSchema` at boot. The set
   starts empty and stays empty.
2. **No leader-election URL.** `knative/services/base/agent-scheduler-service.yaml`
   sets `TZ`, `NATS_URL`, `POSTGRES_{DB,USER,PASSWORD}` and
   `PLATFORM_ENVIRONMENT` — and nothing else. With
   `LEADER_ELECTION_POSTGRES_URL` unset, `SchedulerService.start()` takes the
   "no URL and no known tenants" branch straight into `startLeaderRetryLoop`,
   whose 10 s tick returns early on the same condition; `startScheduler()` is
   never called. `tryAcquireLeadership(undefined)` also returns `false`
   outright, so neither path can promote the pod.
3. **The heartbeat never fires.** `HeartbeatService.publishHeartbeats` returns
   early when `getActiveTenants()` is empty, and `markTenantActive` has no
   caller in this service (`rg markTenantActive services` matches only
   agent-ai-service's same-named method and this service's own unit spec).
   Nothing subscribes to `SCHEDULER_HEARTBEAT` either.
4. **No `REDIS_URL` in the manifest**, so `ExecutionHistoryService` falls back
   to `redis://localhost:6379`; both its methods catch-and-log, so
   `/admin/executions` degrades to `[]` rather than erroring.

Blockers 1 and 2 are mutually reinforcing (the retry loop's escape condition is
"a URL OR a known tenant", and neither can ever become true), so the deployed
pod is a no-op that logs "No tenants known yet" and nothing else. This is
behaviour nobody could want, and it is invisible from the outside because
`/health` returns `status: "ok"` with `checks.database: "idle"` the whole time.
Per ground rule 1 this loop only reports it. T09 rules whether the service is
meant to be live (→ a code loop: seed tenants, set the two env vars) or is
parked (→ say so in the README banner and consider scaling the ksvc to 0).
